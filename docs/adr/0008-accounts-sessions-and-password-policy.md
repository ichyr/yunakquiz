# Accounts, sessions, password policy and pepper

Anyone can still browse and take Quizzes as a Guest. To author, a person registers an Account with an email, a unique display name and a password, and verifies the email. We keep the design small and standard: server-side sessions, argon2id hashes with a versioned pepper, and generic responses that leak nothing about which emails have Accounts. The user stories are in issue #70.

**Passwords follow NIST SP 800-63B, not the first ask.** The first ask was upper case, lower case, a digit and a symbol. We chose instead a length of 15 to 128 characters with no composition rules, Unicode and spaces allowed, NFKC-normalised. Composition rules push people to `Password1!`, which is weak and still passes; NIST SP 800-63B drops them and asks for a blocklist instead. `validatePassword(password, { email, name })` in `packages/core` (ADR 0002) is offline and pure. It rejects passwords that are too short or too long, that are in the bundled common-password list (`zxcvbn-ts` dictionaries), that contain the email local part or the display name, or that are trivial sequences or repeats. The message says which rule failed. This deviates from the first ask on purpose. Checking against breached-password services (HIBP) is a later roadmap ticket.

**Hashing and pepper.** Passwords are hashed with argon2id (`@node-rs/argon2`) at the OWASP minimum parameters: 19 MiB, 2 iterations, parallelism 1. The salt is random per password and lives inside the encoded hash string. A pepper is a secret kept outside the database and passed to argon2 as its `secret` parameter, so a stolen database alone cannot be attacked offline. `PASSWORD_PEPPERS=v2:<secret>,v1:<secret>` lists the peppers; the first is current. Each Account row stores `pepper_version`, which selects the pepper at verify time. A login under an old version or old parameters rehashes under the current ones. The API refuses to start without a pepper. How this works, and what rotation means, is in [docs/password-hashing.md](../password-hashing.md).

**Sessions are server-side, in Postgres.** Session ids, verification tokens and reset tokens are 32 random bytes (`crypto.randomBytes`), base64url; only the SHA-256 hash is stored, so a leaked table is not a set of working cookies. A session ends after 1 hour of inactivity or 12 hours in total, whichever comes first. Logout deletes the row. A password change or reset deletes all of the Account's sessions. Verification tokens last 24 hours and reset tokens 1 hour; both are single-use. We chose server-side sessions over JWTs because logout and password reset must take effect at once, and a JWT cannot be revoked without a server-side list anyway.

**CSRF.** The session cookie is httpOnly, `SameSite=Lax`, and `Secure` in production. Mutating routes also require a custom header (for example `X-Requested-With`), which a cross-site form cannot set. CORS is a strict allowlist. Web and API share a registrable domain in production, so the `SameSite=Lax` cookie is sent. No separate CSRF token is needed.

**Generic responses.** Register, login and reset give the same response and take about the same time whether or not the email has an Account: mail is sent asynchronously and an unknown email still runs a dummy hash. Registering an existing email sends that address a mail saying it already has an Account, with links to log in or reset. A taken display name returns an explicit error, because display names are public anyway. These routes get stricter rate limits, per IP and per email, than the global limit.

**Roles and authorization.** There are two roles, `user` and `admin`; a Guest has no Account. Permission checks are pure functions in `packages/core` (`canEditQuiz`, `canDeleteUser`, and similar): coarse role checks plus ownership. The API enforces them and maps denial to 403; the web app uses them only to hide controls. There is no permissions table.

Hand-rolled auth versus a library is ADR 0010. Quiz authoring is ADR 0009.
